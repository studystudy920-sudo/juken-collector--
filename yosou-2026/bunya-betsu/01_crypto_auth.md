### 分野: 暗号・認証・PKI(パスキー/FIDO2/OAuth/OIDC含む)

### 【午前II 予想問題】

**問1 (春想定)** OAuth 2.0 の認可コードフローに PKCE(Proof Key for Code Exchange)を適用する主目的として、最も適切なものはどれか。

- ア アクセストークンを JWT 形式にし、リソースサーバでの署名検証を可能にする。
- イ 認可サーバとリソースサーバ間の通信を相互 TLS で保護する。
- ウ 悪意のあるアプリによる認可コードの横取りを防ぎ、正規クライアント(元の認可要求を出した主体)だけがトークンと交換できるようにする。
- エ リフレッシュトークンの有効期限を延長し、再認可の頻度を下げる。

**正解**: ウ
**解説**: PKCE(RFC 7636)は主にネイティブ/SPA など公開クライアントでの認可コード横取り(Authorization Code Interception)対策。クライアントが認可要求ごとに `code_verifier`(高エントロピー乱数)を生成し、そのハッシュ `code_challenge`(通常 S256)を認可要求時に送付、トークン交換時に元の `code_verifier` を提示する。認可サーバがハッシュ照合することで、コードを横取りした第三者は `code_verifier` を知らずトークン交換できない。なお選択肢ウは「検知」ではなく「交換の阻止(binding)」が本質である点に注意。ア・イ・エはいずれも PKCE の目的ではない。

**問2 (春想定)** FIDO2/WebAuthn によるパスキー認証がフィッシングに耐性をもつ根本的な理由として、最も適切なものはどれか。

- ア 認証のたびにワンタイムパスワードを生成し、一定時間で失効させるため。
- イ 署名対象データにアクセス先のオリジン情報がバインドされ、RP(リライングパーティ)がオリジンの一致を検証するため、偽ドメインでは署名検証が成立しない。
- ウ 秘密鍵をサーバ側にも複製保管し、突合により本人性を確認するため。
- エ 利用者が入力したパスワードをソルト付きハッシュで保存するため。

**正解**: イ
**解説**: WebAuthn ではブラウザが生成する clientData に乱数チャレンジとオリジンが含まれ、認証器はそのハッシュ(および rpIdHash を含む authenticatorData)に署名する。RP は署名検証時に、clientData 内のオリジンおよび authenticatorData 内の rpIdHash が期待値と一致するかを検証するため、オリジンの異なる偽サイトでは検証に失敗する。加えてブラウザは資格情報を rpId に紐づくオリジンでしか呼び出さない。ウは誤りで秘密鍵は認証器内に留まりサーバへ渡らない。OTP やパスワードハッシュ(ア・エ)はフィッシング耐性の本質ではない(AiTM 中継で OTP は突破され得る)。

**問3 (春想定)** OpenID Connect(OIDC)における ID トークンに関する記述のうち、適切なものはどれか。

- ア ID トークンは JWS で署名された JWT であり、iss・aud・exp・(要求時は)nonce 等のクレームを検証して初めて認証結果として信頼できる。
- イ ID トークンは認可(アクセス権の委譲)そのものを表し、リソースアクセスに直接使用する。
- ウ ID トークンの署名検証には、クライアントとサーバで事前共有した対称鍵のみを用いる。
- エ ID トークンは平文の JSON であり、TLS 上で送るため署名は不要である。

**正解**: ア
**解説**: OIDC は OAuth 2.0 上に構築した「認証」層で、ID トークン(JWT)により「誰が認証されたか」を伝える。受信側(クライアント/RP)は署名(公開クライアントでは通常 RS256、JWKS から `kid` で公開鍵取得)と iss(発行者)/aud(自分宛か)/exp(期限)を必ず検証し、リプレイ防止のため要求時は nonce も照合する。イはアクセストークンの役割で認証と認可の混同、ウは非対称鍵(RS256/ES256 等)が一般的で「対称鍵のみ」は誤り、エは改ざん検知のため署名が必須で誤り。

**問4 (秋想定)** 電子証明書の失効確認方式である OCSP と、そのプライバシ・可用性上の課題を改善する OCSP ステープリングに関する記述のうち、適切なものはどれか。

- ア OCSP ステープリングでは、クライアントが検証対象サーバごとに OCSP レスポンダへ直接問い合わせるため、利用者のアクセス先が OCSP レスポンダに漏れる。
- イ OCSP ステープリングでは、サーバがあらかじめ取得した有効期限付きの署名済み OCSP レスポンスを TLS ハンドシェイク時にクライアントへ提示する。
- ウ OCSP は CRL 全体をダウンロードして失効を確認する方式であり、証明書ごとの個別問い合わせはできない。
- エ OCSP ステープリングを用いると、失効情報の署名者は当該 Web サーバ自身になる。

**正解**: イ
**解説**: OCSP ステープリングは、サーバが CA(OCSP レスポンダ)から取得した署名済みレスポンスを TLS ハンドシェイクに添付(staple)し、Certificate Status として提示する方式。クライアントがレスポンダへ直接問い合わせないため、アクセス先の漏えい(アはステープリングでない従来 OCSP の課題)を防ぎ、レスポンダの負荷・可用性依存も下げる。ウは CRL の説明(OCSP は証明書ごとの個別問い合わせが可能)、エは署名者はあくまで CA(OCSP レスポンダ)であり Web サーバではないので誤り。

**問5 (秋想定)** サーバ間 API 通信で mTLS(相互 TLS)と、証明書にバインドしたアクセストークン(certificate-bound token, RFC 8705)を組み合わせる主目的として、最も適切なものはどれか。

- ア トークンが漏えいしても、対応するクライアント証明書の秘密鍵を持たない第三者は当該トークンを使えないようにする。
- イ トークンのペイロードを暗号化し、リソースサーバ以外が内容を読めないようにする。
- ウ トークンの有効期限を無期限にし、再発行を不要にする。
- エ クライアントがパスワードを送信することで多要素認証を実現する。

**正解**: ア
**解説**: certificate-bound token(RFC 8705)は、アクセストークンを mTLS で提示したクライアント証明書のサムプリント(確認方法クレーム `cnf` の `x5t#S256`)に束縛する。リソースサーバはトークン提示時の mTLS 証明書のハッシュと `cnf` を照合するため、トークンを盗まれても正規クライアント証明書の秘密鍵がなければ利用できず、ベアラトークンの盗難再利用(トークンリプレイ)を防ぐ。ゼロトラストのサービス間通信で有効。イ・ウ・エはいずれも目的ではない。

**問6 (秋想定)** 耐量子計算機暗号(PQC)への移行に関する記述のうち、最も適切なものはどれか。

- ア 現行の RSA や楕円曲線暗号(ECC)による鍵交換・署名は、量子計算機のショアのアルゴリズムにより危殆化する恐れがあるため、格子ベース等の PQC への移行が検討されている。
- イ PQC は情報理論的安全性をもち、計算能力に依存せず解読不能であることが数学的に保証されている。
- ウ 移行期には安全性の観点から、従来暗号と PQC を併用するハイブリッド鍵交換は避け、PQC 単独に一括で切り替えるべきである。
- エ 共通鍵暗号 AES-256 はグローバ(Grover)の探索により実質的な安全性が完全に失われるため、PQC 移行では真っ先に廃止される。

**正解**: ア
**解説**: ショアのアルゴリズムは素因数分解・離散対数を多項式時間で解くため、RSA/ECC など公開鍵暗号が危殆化する。対策として NIST 標準化(ML-KEM(FIPS 203)/ML-DSA 等の格子ベース)や CRYPTREC の検討が進む。イは誤りで、PQC の安全性は格子問題等の計算量的仮定に依存し、情報理論的安全ではない。ウは逆で、実装バグや PQC 自体の未成熟に備え移行期はハイブリッド鍵交換(従来+PQC の両方を破らないと解けない構成)が推奨される。エは誤りで、グローバは探索計算量を平方根に下げる(実効鍵長が半減=AES-256 は約 128 ビット相当)にとどまり、AES-256 なら量子環境でも十分安全とされる。

### 【午後 予想問題(記述式)】

**問1 (春想定)** 社内SaaSへのパスワードレス認証導入

E社は従業員約2,000名の商社であり、複数の社内 SaaS を ID 連携基盤(IdP)経由でシングルサインオン(SSO)している。従来はパスワード+SMS ワンタイムパスワード(OTP)による多要素認証を用いていたが、フィッシングサイトに誘導されて OTP まで入力させられる中間者型フィッシング(AiTM)による不正ログインが発生した。攻撃者は正規サイトを模した偽ページで利用者の認証情報と OTP をリアルタイムに中継(リバースプロキシ)し、発行されたセッションクッキーを窃取していた。E社は対策として FIDO2/WebAuthn によるパスキー認証への移行を計画し、IdP のフェデレーションは OIDC を用いる。移行にあたり、利用者利便性(機種変更・可用性)とセキュリティのバランスが論点となった。

設問1 今回の AiTM フィッシングにおいて、パスワード+SMS OTP が突破された一方、FIDO2/WebAuthn では認証が成立しない。その理由を、WebAuthn の署名検証の仕組みに触れて 60 字程度で述べよ。

設問2 攻撃者は認証後に発行されたセッションクッキーを窃取して不正利用した。パスキー導入後もこの種のセッション乗っ取り(トークン/クッキーの持ち出し再利用)が残存し得る。これを緩和する技術的対策を、鍵所有の証明によるバインドの観点から一つ挙げよ。

設問3 パスキーには、認証器に固定される device-bound passkey と、クラウド経由で複数デバイスに同期される synced passkey がある。機種変更時の可用性を重視して synced passkey を採用する場合に生じるセキュリティ上の留意点を一つ述べよ。

**解答例**:
- 設問1: WebAuthn では認証器がアクセス先のオリジンを含むデータに署名し、RP がそのオリジンの一致を検証するため、ドメインの異なる偽サイトでは署名検証が成立しないから。
- 設問2: アクセストークンやセッションを、クライアントが秘密鍵の所有を証明する送信者制約トークン(RFC 8705 の証明書バインドトークン、RFC 9449 の DPoP、ブラウザ資格情報なら DBSC 等)に束縛し、秘密鍵を持たない第三者による窃取クッキー/トークンの再利用を防ぐ。
- 設問3: 秘密鍵がクラウドの同期アカウントに保管・同期されるため、同期先クラウドアカウントの認証強度・回復手段が実質的な鍵の防御境界となり、そのアカウントが乗っ取られると複数デバイスの資格情報が一括で危殆化する点(認証器内に鍵が留まる device-bound より攻撃面が広がる)。

**採点のポイント**:
- 設問1は「オリジン(ドメイン)を署名対象にバインドし RP が検証する」ことに言及していれば可。単に「秘密鍵が漏れない/認証器から出ない」だけでは、フィッシング耐性の説明として不十分(それは鍵漏えい耐性であり別論点)なので減点。
- 設問2は、トークン/クッキーをクライアントの秘密鍵所有の証明に束縛する趣旨(certificate-bound token、DPoP、DBSC 等の sender-constrained/proof-of-possession)が書けているか。単に「クッキーを暗号化」「有効期限を短くする」だけでは緩和にとどまり主眼を外すため減点。
- 設問3は「同期用クラウドアカウントが新たな攻撃対象/防御境界になり、乗っ取り時に複数デバイスへ波及する」旨が書けているか。利便性(可用性)の裏返しとしてのリスクを捉えているかを評価。

**問2 (秋想定)** 外部 API 連携における OAuth 2.0 と PKI 運用

F社は自社の会計 SaaS を外部の経費精算サービス(P社)に連携させるため、OAuth 2.0 認可コードフロー+PKCE で API アクセスを委譲する設計を進めている。アクセストークンは JWT 形式で、F社認可サーバが秘密鍵で署名し、リソースサーバは JWKS エンドポイントから取得した公開鍵で検証する。設計レビューで、次の指摘が挙がった。(a) リソースサーバでのトークン検証項目が「署名検証のみ」となっている、(b) 認可サーバ署名鍵の失効・更新手順が未定義、(c) リダイレクト URI の登録が「前方一致」で登録されている。F社セキュリティ担当は本番稼働前にこれらを是正する必要がある。

設問1 指摘(a)について、リソースサーバが JWT アクセストークンを受理する際に、署名検証に加えて確認すべきクレームを二つ挙げ、それぞれ検証しない場合に生じるリスクを述べよ。

設問2 指摘(b)について、JWKS を用いた署名鍵のローテーション(更新)を、稼働中のトークン検証を中断させずに行うための運用上の工夫を一つ述べよ。

設問3 指摘(c)について、リダイレクト URI を「前方一致(部分一致)」で登録することの危険性を、OAuth の攻撃手法に触れて述べ、あるべき登録方法を答えよ。

**解答例**:
- 設問1: (1) aud(受信者)を検証しないと、他リソースサーバ向けに発行されたトークンを自リソースサーバが誤って受理し、トークンの転用(混同)を許す。(2) exp(有効期限)を検証しないと、期限切れの古いトークンや盗用トークンが失効後も受理され、不正アクセスが継続する。(iss(発行者)や nbf(有効化前拒否)でも可)
- 設問2: JWKS に各鍵を kid(キー識別子)付きで複数併存させ、新旧の鍵を一定のオーバーラップ期間並行公開する。新規発行トークンは新鍵の kid で署名し、検証側は JWT ヘッダの kid で対応鍵を選択、旧鍵で署名済みのトークンが全て失効した後に旧鍵を JWKS から撤去する(あわせて JWKS のキャッシュ TTL を考慮し、鍵追加後に反映猶予をおいてから署名鍵を切り替える)。
- 設問3: 前方一致では、攻撃者が登録済み URI の後方にパスやクエリ、オープンリダイレクタ経由の遷移先を付加した URI をリダイレクト先に指定でき、認可コードを攻撃者の管理先へ送らせる認可コード横取り/オープンリダイレクト悪用につながる。リダイレクト URI は完全一致(exact match)で事前登録すべきである。

**採点のポイント**:
- 設問1は aud/exp/iss/nbf 等から二つ挙げ、各々の未検証リスク(トークン転用・混同、失効/期限切れトークンの受理継続)まで結びついているか。クレーム名の列挙のみは減点。
- 設問2は「kid による複数鍵の並行公開」「新旧鍵のオーバーラップ期間」に相当する運用が書けているか。JWKS キャッシュ TTL への配慮まで触れれば加点。単に「鍵を変える」だけでは不十分。
- 設問3は前方一致/部分一致がリダイレクト先の悪用(認可コード横取り・オープンリダイレクト悪用)を招く点と、是正策=完全一致登録の双方が書けているか。両方揃って満点、片方のみは部分点。
